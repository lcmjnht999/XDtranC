## 问题、用户与证据

面向熟悉 C++、不熟悉仓颉的迁移开发者：直接逐文件翻译容易遗漏跨文件声明、超出模型上下文，且生成的文件可能为空、漏项或无法追溯。工具把导入、切分、转换草稿和完整性清单连成可检查的本地流程，方便人工接手。

证据分三层：PRD 的用户画像和任务描述提供问题假设；[研究底稿](../research-xdtranc.md)提供仓颉文档、相邻迁移工具和论文的查证入口，但状态为 Partial research，多项来源没有核验日期；解析、依赖、遗漏和失败路径的离线测试说明这些工程风险确实需要处理。后两者不能替代真实用户需求调研。

目前没有提供用户访谈原始记录、人工迁移耗时对照或真实项目收益数据。不能声称已证明节省多少时间，也不把其他工具的效果、厂商宣传或研究线索当成本项目结果。问题价值仍需用户试用或访谈补证；本次没有联网复核研究资料。

## 设计选择与可解释性

Electron保留本地文件交互，TypeScript贯穿桌面与引擎；代价是包体和启动资源。engine不依赖Electron，CLI和桌面调用同一套解析、切分、转换及导出服务。shared只保留一份输出契约与配置规则，减少两端行为漂移。

tree-sitter提供语法结构，不引入完整Clang编译环境；代价是模板/重载等语义需要显式限制。JSON checkpoint适合单用户工作区，省去数据库；代价是持久化失败必须中断，并处理文件占用。Monaco延迟加载；当前构建仍有大分块警告。LLM只返回结构化数据，不持工具权限，路径校验和写盘由引擎负责。

自核查是模型输出的一部分，不是独立正确性证明。引擎另做schema、路径、文件/符号覆盖与空壳检查；仍可能漏掉“符号存在但函数逻辑错误”。例如E05的低行保留用例可出现转换/导出complete、空壳判定failed；E06 API夹具截图的符号覆盖仅1/3，明确显示不通过。这些证据应保留，不能为演示成功而改成全绿。
